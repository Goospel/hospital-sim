# T-076 · 커밋할 게 없는 유령 `M` — 앱이 LF로 쓰고 autocrlf가 CRLF로 푼다

- **증상**: `.obsidian/app.json`이 `git status`에 항상 ` M`으로 떠 있다. 그런데 `git diff`는 **아무 줄도 출력하지 않는다**(경고 `LF will be replaced by CRLF the next time Git touches it`만 나옴). `git checkout --`로 되돌려도, `git stash`로 치워도 잠시 뒤 다시 `M`. pull 할 때마다 "로컬 수정이 있으니 stash부터" 하는 헛수고가 붙고, 무엇보다 `git status`로 *"지금 내가 뭘 건드렸나"*를 읽을 수 없다.

- **원인**: **커밋할 변경이 애초에 0이다.** 해시로 확정했다 — 인덱스 blob(`git rev-parse :.obsidian/app.json`)과 worktree(`git hash-object`)가 **동일**(`c9e454e`). 유령 `M`의 정체는 EOL 왕복이다: 이 머신은 `core.autocrlf=true`라 git이 체크아웃 때 파일을 **CRLF**로 푼다(`git ls-files --eol` → `i/lf w/crlf`, 이 상태는 깨끗). 그런데 **옵시디언은 크로스플랫폼 앱이라 자기 설정을 항상 LF로 되쓴다** → worktree가 `w/lf`로 바뀌는 순간 git이 `M`을 표시한다(정규화하면 blob과 같아 diff는 0줄). 즉 앱이 설정을 한 번 저장할 때마다 재발하는 **구조적** 잡음이고, 파일을 되돌리는 어떤 조치로도 안 끝난다 — 되돌릴 내용 차이가 없으니까.

- **해결**: `.gitattributes`에 `.obsidian/** text eol=lf` — git이 이 경로를 CRLF로 풀려는 시도 자체를 포기하게 못박는다. 이미 커밋된 blob이 LF라 `git add --renormalize .obsidian/`은 변경 0(확인). 검증은 재현으로 했다: ①강제 재체크아웃 → `w/lf`(전엔 `w/crlf`) ②앱 저장 시뮬레이션(LF로 되쓰기) → `status` 깨끗(전엔 `M`). **급할 때의 임시 처방은 `git add <파일>`** — stat 캐시만 갱신돼 `M`이 사라지고, 해시가 같으니 스테이징되는 변경도 0이다(다음 체크아웃에 재발).

- **재발방지**: ① **`git diff`가 0줄인데 `status`가 `M`이면 내용 문제가 아니다 — EOL/필터 문제다.** 진단은 눈에 보이는 diff가 아니라 **해시와 `git ls-files --eol`**로 한다(`i/…  w/…`가 갈리면 확정). ② **크로스플랫폼 앱이 관리하는 설정 파일(`.obsidian/`, `.vscode/`, 각종 dotfile JSON)은 `text eol=lf`로 못박는다** — `core.autocrlf=true`와 앱의 LF 고집이 영구히 싸우고, 이긴 쪽이 없어 잡음만 남는다. ③ 오진 주의 — 이 건에서 `od -c | grep -o '\r'`로 CR을 세려 했는데 GNU grep이 `\r`을 문자 `r`로 폴백해 **"CR 5개"라는 가짜 측정**이 나왔고(실제 0개), 그걸 근거로 "커밋된 blob이 혼합 EOL"이라 한 번 잘못 짚었다. EOL 측정은 `od -c` **원문을 눈으로 보거나** `git ls-files --eol`로 한다. 이건 「Windows 셸 한글·인코딩 원칙」이 경고한 *Git Bash 도구의 무성 실패*와 같은 계열이다.
