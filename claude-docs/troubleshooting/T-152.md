# T-152 · 돌연변이 치환이 CRLF에서 무성 no-op — 계측기가 아무것도 안 했는데 통과로 읽힌다

- **증상**: 채용 패널 그래픽 재설계 Task 1(2026-08-03)에서 스프라이트 규칙을 겨눈
  테스트가 진짜 판별력이 있는지 확인하려고 **소스를 임시 변조하는 치환 스크립트**를
  돌렸는데, 테스트가 그대로 초록이었다. 에러 0·경고 0. 표면상 결론은 *"이 테스트는
  공허하다"* 였지만, 실제로는 **파일이 한 바이트도 안 바뀌어 있었다** — 변조 자체가
  일어나지 않았다.

- **원인**: 이 저장소의 작업 트리는 **EOL이 파일마다 다르다**(실측 2026-08-03:
  `PixelSprite.tsx` CRLF 547줄·`globals.css` CRLF 134줄 · `hirePanel.test.tsx`는
  LF 169줄). 그런데 치환 패턴을 소스에서 눈으로 옮겨 적으면 줄바꿈은 자연히 `\n`이
  된다 — CRLF 파일에서 그 패턴은 **매치가 0건**이고, JS `String.replace`는 못 찾으면
  **예외 없이 원본을 그대로 돌려준다**:

  ```
  s.includes('const HAIR_PATHS = [\n')    → false
  s.includes('const HAIR_PATHS = [\r\n')  → true
  s.replace(패턴, 'MUTATED') 이 바꾼 바이트 수 → 0
  ```

  같은 스크립트가 LF 파일에서는 정상 동작하기 때문에 **한 번 성공한 방식이 다음
  파일에서 조용히 죽는다** — 이 혼재가 함정을 예측 불가로 만든다.

- **해결**: 치환은 **여러 줄 패턴을 피하고 한 줄 안의 유일한 부분 문자열**을 쓴다
  (예: `--ink-3: #5a533f` → `--ink-3: #585039`). 줄을 걸쳐야만 한다면 `\r?\n`
  정규식으로 쓴다. 그리고 **바뀌었는지를 반드시 확인한다** — `out.length === s.length`
  이거나 `out === s`면 그 자리에서 `throw`. 이번 ink-3 작업의 두 돌연변이는
  이 방식으로 각각 「대비 하한」·「잉크 3단 서열」 테스트를 실제로 죽이는 것을
  확인했다.

- **재발방지**: **돌연변이 확인은 계측기의 계측기다 — 그것이 무성 실패하면 보고서에
  「돌연변이 확인함」이라고 적히면서 실제로는 아무것도 확인되지 않는다.** 그래서
  이 절차의 실패는 테스트 실패보다 나쁘다(초록불이 거짓말을 한다). 규칙:
  ① 치환 후 원본과 다른지 **프로그램이 검사**하고 다르지 않으면 크래시시킨다
  ② 치환 성공을 확인한 뒤에야 테스트를 돌린다 ③ 되돌린 뒤 `git diff`가 비었는지 본다.
  글로벌 「Windows 셸 한글·인코딩 원칙」 3번(BOM·EOL 보존)과 뿌리가 같지만 피해가
  다르다 — 그쪽은 phantom diff(눈에 보임), 이쪽은 **거짓 검증 통과**(안 보임)다.
