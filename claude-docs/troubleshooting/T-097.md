# T-097 · SDK `timeout`은 1회당 — 기본 `maxRetries: 2`가 타임아웃 계약을 3배로 늘린다

- **증상**: 림월드형 2주차 PR D Task 5(LLM 프록시, 2026-07-28 · 커밋 `80388ae`)에서 라우트에 `timeout: 9_000`(9초)을 걸었는데 리뷰 실측에서 한 요청이 **28.45초**만에 끝났다(재시도 3회). 클라이언트는 AbortController 10초에 이미 끊고 폴백 문장으로 강등된 뒤였으므로, 서버는 **아무도 안 받는 응답을 18초 더 기다리며 토큰 값을 쓴 것**이다. 계약(9초 < 10초)이 성립한다고 믿고 있던 자리다.

- **원인**: TS SDK의 `timeout`은 **요청 1회당** 상한이고, 기본 `maxRetries: 2`는 **타임아웃도 재시도 대상으로 본다**. 그래서 실효 최대 대기는 9초 × 3회 + 백오프 = 실측 28.45초다. 설정한 숫자와 계약하는 숫자가 갈리는 자리 — `timeout`을 "이 호출이 최대 이만큼 걸린다"로 읽으면 **조용히 3배 틀린다**. 게다가 재시도가 버는 것은 성공률인데 그 성공은 클라이언트가 이미 끊은 뒤에 도착하므로, 이 배치에서 재시도는 **성공률을 0만큼 올리고 비용만 3배로 만든다**.

- **해결**: `maxRetries: 0`([src/app/api/storyteller/route.ts](../../src/app/api/storyteller/route.ts)). 이 게임은 LLM 실패를 결정론 폴백 문장이 이미 받으므로 SDK 재시도가 살 이유가 없다 — 최종 안전망이 앱 안에 있는데 네트워크 층에서 한 번 더 버티는 것은 중복이 아니라 손해다. 재시도를 되살리려면 **합계가 클라이언트 상한 안에 들도록** per-request timeout을 나눠야 한다(예: 3초 × 3회)는 조건을 상수 주석에 함께 남겼다.

- **재발방지**: ① SDK 타임아웃을 설정할 땐 **재시도 정책을 같은 자리에서** 정한다 — 둘 중 하나만 적으면 실효 상한이 암묵값이 되고, 그 암묵값은 라이브러리 버전이 바뀌면 말없이 움직인다 ② 클라이언트·서버 양쪽에 상한이 있으면 **「서버 실효 상한 < 클라이언트 상한」을 부등식으로 적어 둔다** — 여기선 9초 < 10초가 의도였는데 실제는 27초 > 10초였고, 부등식을 적어 뒀다면 `maxRetries`를 안 볼 수 없었다 ③ **이 계열은 green으로 안 잡힌다** — 테스트는 모킹된 fetch를 보고, 실효 상한은 실호출에서만 드러난다. 새 SDK를 붙일 땐 기본값 표(`timeout`·`maxRetries`·`max_tokens`가 사고를 합산하는지)를 **한 번 읽고 지나간다** ④ 같은 상수 옆의 단위 함정도 함께: TS SDK의 `timeout`은 **밀리초**, Python SDK는 초다(9로 쓰면 9ms가 되어 전부 타임아웃).
