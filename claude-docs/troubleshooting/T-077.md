# T-077 · Windows에서 `npm ci`가 ENOTEMPTY로 죽는다 — 지우기 단계의 파일 잠금 경합

- **증상**: `git pull`(66커밋, `package.json`·`package-lock.json` 변경)로 의존성이 바뀐 뒤 `npm ci`가 즉시 실패한다.

  ```
  npm error code ENOTEMPTY
  npm error syscall rmdir
  npm error path C:\...\node_modules\caniuse-lite\data\features
  npm error errno -4051
  ```
  경로는 매번 다르게 나온다(`caniuse-lite`는 우연히 걸린 희생자 — 파일이 많은 패키지가 잘 걸린다).

- **원인**: `npm ci`는 정의상 **기존 `node_modules`를 통째로 지우고** 락파일대로 다시 설치한다. Windows에서 이 대량 삭제가 파일 핸들을 잡고 있는 다른 프로세스(실시간 검사 백신, 인덱서, 열려 있는 에디터, 실행 중인 dev 서버)와 경합하면, 하위 파일 삭제가 끝나기 전에 `rmdir`이 호출돼 "디렉터리가 비어 있지 않다"로 죽는다. **npm 잘못도 락파일 문제도 아니다** — 그래서 `npm cache clean`·`--force` 류는 헛수고다. 이번 건에서 실행 중인 node 프로세스를 전수 조사했는데(`Get-CimInstance Win32_Process -Filter "Name='node.exe'"` 로 커맨드라인까지) 이 프로젝트의 dev 서버는 **없었다** — 즉 범인 프로세스를 특정할 수 없는 순수 타이밍 경합이었다.

- **해결**: `node_modules`를 **직접 지운 뒤** 재실행한다. 34초에 394패키지로 통과했다.

  ```powershell
  Remove-Item -Recurse -Force node_modules
  npm ci
  ```

- **재발방지**: ① **`npm ci`가 ENOTEMPTY/EPERM/EBUSY로 죽으면 재시도하지 말고 `node_modules`를 먼저 직접 지운다** — 같은 명령을 그대로 다시 돌리면 같은 삭제 단계에서 같은 경합을 다시 밟는다. ② 다만 **범인 프로세스를 먼저 확인하라** — dev 서버가 실제로 떠 있으면 지우기가 또 실패한다. 프로세스 이름만 보면 Claude Code·MCP 서버까지 섞여 나오니(그걸 죽이면 세션이 끊긴다) **커맨드라인으로 대상을 확인하고** 이 프로젝트 경로를 잡은 것만 종료한다. ③ dev 서버는 Bash로 띄우지 않는다(이 저장소 규약 — `preview_start`) — 어느 셸이 서버를 붙잡고 있는지 추적 못 하는 상황 자체를 안 만드는 게 이 경합의 근원 차단이다.
