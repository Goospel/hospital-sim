# T-083 · PowerShell 배열 언랩 — 1건과 0건이 구분되지 않아 테스트가 거짓 실패했다

- **증상**: 훅 로깅 테스트에서 로그가 정상 기록됐는데도 `로그 1줄` 단정이 실패했다. 실패 메시지는 값이 비어 있었다 — `"실제: $($r.Count)줄"`이 **`실제: 줄`**로 찍혔다(`$r.Count`가 `$null`). 로그 2줄을 기대하는 케이스만 통과해서, 얼핏 "1줄일 때만 기록이 안 된다"는 이상한 구현 버그로 보였다.

- **원인**: 테스트 헬퍼가 이랬다.

  ```powershell
  function Get-LogRecords {
    ...
    return @($lines | ForEach-Object { $_ | ConvertFrom-Json })
  }
  $r = Get-LogRecords     # ← 여기서 언랩된다
  ```

  함수 안에서 `@()`로 감쌌지만 **PowerShell은 함수가 요소 1개짜리 배열을 반환할 때 그것을 언랩해 스칼라로 돌려준다.** 그래서 `$r`은 배열이 아니라 `PSCustomObject` 하나가 되고, `ConvertFrom-Json`이 만든 `PSCustomObject`에는 `.Count`가 없어 `$null`이 된다. `$null -eq 1`은 거짓이므로 단정이 깨진다.

  요소가 2개일 때는 배열이 유지돼 `.Count`가 정상이었다 — **그래서 "2줄 케이스만 통과"라는 오해를 부르는 증상 패턴**이 나왔다. 로그 파일 자체는 처음부터 옳게 기록되고 있었고, 잘못된 건 계측기 쪽이었다.

- **해결**: 함수 **호출부**에서 `@()`로 감쌌다.

  ```powershell
  $r = @(Get-LogRecords)
  ```

  함수 내부의 `@()`는 언랩을 막지 못한다 — 언랩은 반환 경계에서 일어나므로 **받는 쪽에서** 강제해야 한다. 이 한 줄로 5건이 즉시 통과했고, 구현은 전혀 손대지 않았다.

- **재발방지**: **PowerShell에서 "0건/1건/N건"을 세는 코드는 받는 쪽을 `@()`로 감싼다.** 특히 테스트에서 `.Count`로 개수를 단정할 때 필수다 — 감싸지 않으면 **0건과 1건이 똑같이 `.Count = $null`처럼 보여** 두 상태가 합쳐진다. 같은 이유로 `$x.Count -eq 0`으로 "비었음"을 검사하는 것도 위험하다.

  더 일반적으로: **테스트가 실패하면 구현을 의심하기 전에 계측기부터 의심한다.** 이번엔 "1줄일 때만 기록 실패"라는 물리적으로 이상한 증상이 힌트였다 — 증상이 구현 로직으로 설명되지 않으면 대개 테스트 쪽이 틀렸다. [T-080](T-080.md)·[T-082](T-082.md)가 *"통과하는데 검증 안 하는 테스트"*라면 이건 반대쪽 실패 모드인 *"실패하는데 결함이 없는 테스트"*이고, 둘 다 계측기를 신뢰한 대가다.
