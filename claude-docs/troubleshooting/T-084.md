# T-084 · 1회 관측으로 쓴 부정 결론 — "방법이 없다"는 문서가 탐색을 차단한다

- **증상**: 서브에이전트 설정을 조사하던 한 세션(2026-07-27)에서 **부정 결론을 세 번 냈고 세 번 다 틀렸다.**
  1. *"정의 파일 본문 앞에 빈 줄을 넣으면 경계가 생긴다"* → 파일엔 **이미 빈 줄이 있었다**. 하네스가 본문을 trim하므로 애초에 무효인 처방이었다.
  2. *"정의 파일을 고쳤으면 세션을 새로 시작해야 반영된다"* → 같은 세션에서 한 박자 뒤 다시 띄우니 반영돼 있었다. 실제 현상은 **편집 직후 즉시 호출에만 안 걸리는 짧은 지연**이었다.
  3. *"effort는 세션 안에서 검증할 방법이 없다"* → 트랜스크립트(`subagents/agent-*.jsonl`)의 assistant 항목마다 **최상위 `effort` 키가 있었다.** 훅 입력에도 부모 세션 effort가 실려 있었다.

  ①②는 PR에 적혔고, ③은 **글로벌 `CLAUDE.md`에 박혔다.** 사용자가 *"다른 방법 없나"*라고 되묻지 않았으면 그 문장이 그대로 남았을 것이다.

- **원인**: 셋 다 **한 번 관측하고 일반화**했다. 그리고 부정 결론에는 긍정 결론에 없는 비대칭이 있다 — *"X가 있다"*는 하나만 찾으면 증명되지만 *"X가 없다"*는 **찾지 못했다는 사실**일 뿐이다. 내가 관측한 것은 언제나 "내가 본 자리에 없었다"이고, 그걸 "없다"로 쓰는 순간 **내 탐색 범위가 세계의 경계로 승격된다.**

  ③이 특히 그랬다: 훅 입력에 자식 effort 칸이 없다는 것은 사실이었고, 거기서 *"그러므로 검증 불가"*로 건너뛰었다. **훅(사전 주입)과 트랜스크립트(사후 기록)는 다른 수단인데, 한 수단의 부재를 목적의 부재로 읽었다.** 실제로 훅 입력을 통째로 덤프해 보니 `tool_use_id`와 부모 `effort`까지 있었다 — 덤프는 5분도 안 걸렸는데 그 전에 결론부터 썼다.

  가장 나쁜 부분은 그다음이다. 부정 결론이 문서에 박히면 **다음 세션은 그걸 읽고 탐색 자체를 건너뛴다.** 틀린 긍정("이렇게 하면 된다")은 실행하다 깨지지만, 틀린 부정("방법이 없다")은 **아무도 시도하지 않으므로 반증될 기회가 사라진다.** 문서가 스스로를 보호하는 형태의 고장이다.

- **해결**: 세 건 모두 **한 번 더 확인하자 뒤집혔다.**
  - ② 한 박자 뒤 서브에이전트를 다시 띄움 → 반영 확인 → `CLAUDE.md` 정정
  - ③ 훅 입력 전체를 임시 프로브로 덤프 + 트랜스크립트 파일을 직접 `grep` → `effort` 키 발견 → 검증 경로(`scripts/show-subagent-runs.ps1`)를 만들고 정정
  - ①은 trim이 원인임을 확인해 "정의 파일 쪽에서 완전히 해결 불가"라는 **한계까지 함께** 기록(부정 결론을 지우는 게 아니라 *근거와 범위*를 붙였다)

- **재발방지**: **"없다 / 불가능하다 / 방법이 없다"를 쓰기 전에 두 가지를 한다.** ① 반대 증거가 있을 만한 자리를 **한 곳 더** 판다 — 특히 *"내가 쓰는 수단에 없다"*를 *"어디에도 없다"*로 옮겨 적고 있지 않은지 본다(사전/사후, 입력/출력, 런타임/로그는 서로 다른 자리다). ② 그래도 부정으로 쓸 거면 **관측 횟수와 탐색 범위를 문장에 남긴다** — "1회 관측", "훅 입력 기준"처럼. 범위가 적혀 있으면 다음 사람이 그 바깥을 파 볼 수 있고, 그게 실제로 이번에 ③을 뒤집었다.

  타이밍 규칙 하나: **편집 직후 즉시 확인해서 안 보이면 "안 됨"이 아니라 "아직"일 수 있다**(②가 그랬다). 반영을 확인할 땐 한 박자 뒤 한 번 더 띄운다. [T-080](T-080.md)·[T-082](T-082.md)가 *"green을 판별력의 증거로 착각"*하는 병이라면, 이건 *"관측 부재를 부재의 관측으로 착각"*하는 병이다 — 둘 다 **한 번 더 흔들어 보는 것** 말고 방법이 없다.
