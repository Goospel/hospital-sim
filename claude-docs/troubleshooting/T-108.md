# T-108 · 돌연변이 스크립트의 출력 파싱이 CP949로 죽으면 원복이 통째로 건너뛰어진다

- **증상**: 「간호사 폰 + 수납」 작업에서 계약 17개의 돌연변이 확인을 파이썬 스크립트로 돌렸다. 첫 실행이 `UnicodeDecodeError: 'cp949' codec can't decode byte 0xe2`로 죽었고, 이어서 `TypeError: unsupported operand type(s) for +: 'NoneType' and 'NoneType'`이 났다. 스크립트를 고쳐 다시 돌리려 했더니 **두 번째 실행도 같은 자리에서 죽었다**. 그 시점에 `src/sim/patientFlow.ts`의 `hasCashier`가 이렇게 남아 있었다 — 간호사 조건이 없고, 카운터를 접수처 안에서 찾지도 않는다:
  ```ts
  return w.furniture.filter(f => f.kind === 'COUNTER').map(f => ({ x: f.x + 1, y: f.y }))
  ...
  return cashierSpots(w, blocked, regions).length > 0
  ```
  즉 **M1·M2 돌연변이 두 개가 소스에 그대로 눌러앉아 있었다**. 그대로 커밋했다면 방금 테스트로 못박은 계약 두 개가 코드에서만 사라진 채 나갔을 것이다.

- **원인**: 두 결함이 겹쳤다.
  - ① **출력 파싱이 인코딩에 걸렸다.** `subprocess.run(..., capture_output=True, text=True)`는 이 머신에서 stdout을 **CP949**로 디코딩한다(파이썬의 `locale.getpreferredencoding()`). vitest 출력에는 한글 테스트 이름과 `⎯`·`✓` 같은 UTF-8 기호가 섞여 있어 디코딩이 곧바로 터진다. 글로벌 「Windows 셸 한글·인코딩 원칙」 2번(*인라인 인자의 한글이 CP949로 깨진다*)의 **읽기 방향 쌍둥이**다 — 지금까지 문서화된 것은 쓰기 방향뿐이었다.
  - ② **그 예외가 원복보다 앞이었다.** 루프가 `write(mutant)` → `run` → `parse` → `write(original)` 순서였고, 파싱이 죽으면 마지막 줄에 영영 도달하지 않는다. 게다가 예외가 루프 **밖으로** 튀어 나머지 돌연변이도 안 돌았다. 두 번째 실행이 같은 자리에서 죽은 것도 이 때문이다 — 이미 부서진 소스 위에서 다음 돌연변이를 얹고 또 죽었다.
  - **왜 조용했나**: 스크립트가 죽었으니 화면에는 파이썬 트레이스백이 요란하게 찍힌다. 그런데 그 트레이스백은 *"결과를 못 읽었다"*로만 읽히지 *"소스가 부서진 채 남았다"*로는 안 읽힌다. 실패 모드가 **출력에 안 적히는 자리**에 있었다.

- **해결**: 스크립트를 두 곳 고쳤다.
  - **판정은 종료 코드로만 한다** — `stdout=DEVNULL, stderr=DEVNULL` + `r.returncode != 0`. 돌연변이 확인에 필요한 정보는 "죽었나/살았나" 한 비트뿐이라 출력을 읽을 이유가 애초에 없었다. 인코딩 문제를 **푸는** 대신 그 표면을 **없앴다**.
  - **원복은 `try/finally`** — 어떤 예외가 나도 원본이 돌아온다. 그리고 패치 실패(`s.count(old) != 1`)는 던지지 않고 `PATCH-MISS`로 기록하고 넘어가, 한 항목이 어긋나도 나머지 계약이 계속 측정된다.
  - 되돌린 뒤 전체 1,297건 green을 **다시 확인하고 나서** 돌연변이를 다시 돌렸다(17개 중 16개 사살 · 1개는 등가 돌연변이로 판정).

- **재발방지**:
  - **소스를 임시로 부수는 스크립트는 원복을 `finally`에 둔다.** 돌연변이 확인·프로브·벤치마크가 전부 이 모양이고, 원복이 정상 경로에만 있으면 "실패한 실행"이 곧 "부서진 워킹 트리"가 된다.
  - **그 스크립트를 돌린 뒤에는 반드시 `git diff`(또는 전체 테스트)로 워킹 트리가 깨끗한지 확인한다.** 이번에 잡힌 것도 커밋 전에 소스를 눈으로 다시 읽었기 때문이지 스크립트가 알려줘서가 아니다.
  - **이 머신에서 파이썬 `subprocess`로 툴 출력을 읽지 않는다.** 꼭 읽어야 하면 `encoding='utf-8', errors='replace'`를 **명시**한다(기본값은 CP949다). 훅에서 stdin을 `[Console]::In`으로 읽지 않는 것과 같은 계열의 함정이고, 방향만 반대다.
  - 스크립트 본체는 스크래치패드에 남겼다(`mutate.py`) — 다음에 같은 형태의 확인이 필요하면 이 두 규칙이 이미 박힌 것을 복사한다.

- **재발 (2026-07-30 · 「배경 톤 재조정」)**: **정확히 같은 자리에서 또 밟았다.** 팔레트 돌연변이 확인 스크립트를 `capture_output=True, text=True`로 쓰고 원복을 `finally` 없이 루프 끝에 뒀다 → 첫 항목에서 CP949로 죽고 `treeCanopyLit`이 `#24402e`(원래의 밝은 값)로 **눌러앉았다**. 이번엔 곧바로 `git checkout`으로 되돌리려 했으나 그건 **권한 분류기가 차단**했고(파괴적 작업), 결국 남은 돌연변이 값을 `Grep`으로 찾아 Edit로 되돌렸다 — 즉 **T-108이 이미 있는데도 이 함정은 다시 통과했다**.
  - **왜 문서가 못 막았나**: 재발방지 3개가 전부 *"다음에 스크립트를 쓸 때 기억하라"*는 **소프트 규칙**이라, 스크립트를 새로 짜는 시점에 T-108을 읽을 이유가 없었다(다른 작업·다른 파일이라 검색에 안 걸린다). 이 저장소가 세 번 경고한 *「검사기 없는 규약은 죽는 게 아니라 썩는다」*의 또 한 사례다.
  - **승격 후보(글로벌)**: 이건 이 프로젝트가 아니라 **이 머신**의 함정이라 hookify warn 룰이 제자리다 — `event: bash` · 패턴은 `capture_output` 이 있는데 `errors=` 가 없는 파이썬 호출, 메시지는 「출력을 읽지 말고 종료 코드로 판정 + 원복은 `finally`」. 정규식 한 줄로 되는 계단이라 전용 훅까지 갈 필요가 없다. **이 저장소 밖(글로벌 설정)이라 여기서 만들지 않고 후보로만 남긴다.**
